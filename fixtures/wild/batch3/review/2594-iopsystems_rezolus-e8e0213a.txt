feat(agent): cgroup_attribution option for ext4_ops and xfs_log, off by default (#1359)

* feat(agent): cgroup_attribution option for ext4_ops and xfs_log, off by default

The per-cgroup path in these samplers' end hooks (the cgroup serial
check and two atomics on shared per-cgroup counters) measured 265 ns of
the hook's 535 ns on the null_blk fsync bench, half its cost, and the
bench ran 15% more fsyncs per second without it. It is now the config
option `cgroup_attribution` in the sampler's section (or `[defaults]`),
off by default.

The switch is a `const volatile` global in each BPF program, written
into the skeleton's read-only data before load through a new
`BpfBuilder::pre_load` hook, so with it off the verifier removes the
path from the loaded program rather than testing a flag on every run.
The cgroup maps and ringbuf handler are registered only when it is on,
so the cgroup_ext4_* and cgroup_xfs_log_* series are absent, not zero.

* docs: record the cgroup_attribution decision; assert the read-only data exists

The backlog and the gaps entry described the per-cgroup decision as pending; this branch makes it (opt-in, off by default), so they now say so, and what remains of the default-on question is the 1.13 us per pair that stays. The pre_load closures assert the program's read-only data exists instead of silently loading with the switch off when the config says on (unreachable with libbpf-cargo 0.26, which builds the field from a NonNull, but an invariant is better stated).
