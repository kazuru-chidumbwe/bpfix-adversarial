fix(ebpf): move tls_conn_state off the tcp_sendmsg kprobe stack (#285)

bpf_kprobe_tcp_sendmsg built a struct tls_conn_state (~284 bytes, dominated
by h_powers[16][16]) on its stack, then called bssl_recover_h via a
bpf-to-bpf call. The verifier sums stack frames along a call chain against
the 512-byte limit, so caller + callee reached 768 and the program was
rejected on load:

  combined stack size of 2 calls is 768. Too large

This reproduces on GKE's 6.8 kernel; it slipped through where clang sized
the frames smaller. Back new_conn with a per-CPU scratch map (the same
idiom already used for ghash_scratch/aes_scratch) so it no longer occupies
the kprobe frame. BPF programs run with preemption disabled, so the per-CPU
slot cannot be re-entered mid-execution.

Verified on a 6.8 node: the controller loads all programs and reaches
"eBPF TLS uprobes enabled" instead of crashlooping.

Co-authored-by: Claude Fable 5 <noreply@anthropic.com>
