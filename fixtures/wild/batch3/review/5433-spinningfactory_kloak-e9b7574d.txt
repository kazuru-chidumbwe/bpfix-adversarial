* feat: add eBPF e2e tests to CI with continue-on-error

Runs TestEBPFSecretRewrite in GitHub Actions on every PR. The test
deploys the demo-go app, verifies that the eBPF uprobe rewrites
kloak:UUID → real secret values in-flight (checked via httpbin.org
header echo).

Uses k3d on ubuntu-latest (kernel 6.8+, BPF-capable). Marked as
continue-on-error since eBPF in Docker-in-Docker may not work on
all runner configurations.

  keeps eBPF enabled with privileged + BPF/BTF volumes)

  (defaults to "e2e" for backward compat)

  KLOAK_E2E_OVERLAY=e2e-ebpf, runs with -tags=e2e_ebpf

* feat: generate eBPF bindings at Docker build time for multi-arch (#20)

* feat: generate eBPF bindings at Docker build time for multi-arch support

The eBPF program was compiled with -D__TARGET_ARCH_arm64 and committed
to the repo, but CI runs on x86_64. CO-RE can handle kernel version
differences but not CPU architecture differences (struct pt_regs layout
is fundamentally different between arm64 and x86_64).

Fix: generate eBPF bindings inside the Dockerfile using the build
platform's architecture. Docker buildx sets TARGETARCH automatically;
plain docker build receives it via --build-arg.

Changes:
- Dockerfile: install clang/llvm, run go generate with arch-specific
  KLOAK_TARGET_ARCH before building the Go binary
- Remove pre-committed .o and .go eBPF files from repo (now generated
  at build time)
- go:generate directive: read KLOAK_TARGET_ARCH env var instead of
  hardcoding arm64
- CI: install clang and generate eBPF bindings in lint/build/test jobs
  (needed since generated files are no longer committed)
- .gitignore: revert to ignoring generated eBPF files

FindContainerCgroupPath only had systemd cgroup driver patterns.
K3s uses the cgroupfs driver by default, with paths like:
  /sys/fs/cgroup/kubepods/burstable/pod<UID>/<containerID>

Added:

- Guaranteed QoS class for systemd driver (was missing)
- Walk-based fallback that searches the cgroup tree for the container
  ID, handling non-standard layouts (k3d, minikube, etc.)

This fixes the "cgroup path not found" error that prevented eBPF
uprobe attachment in k3d environments.

* fix: use direct clang compilation for eBPF .o files in Dockerfile

bpf2go's llvm-strip corrupts eBPF object files, producing programs
that compile to 'return 0' (xlated 16B). This affected both Alpine
and Debian-based Docker builds despite the same clang/flags producing
correct bytecode when invoked directly.

Fix: multi-stage Dockerfile where:
1. ebpf-gen stage (Debian): runs bpf2go to generate .go wrapper files,
   then overwrites the .o files with direct clang compilation
2. builder stage (Alpine): copies correct .go + .o files and builds
   the Go binary

Also changed arm64 uprobe register access from PT_REGS_PARMx (CO-RE
macros that get poisoned) to raw bpf_probe_read_kernel with fixed
offsets, matching the x86 code path. And changed function signatures
from 'struct pt_regs *ctx' to 'void *ctx' to avoid CO-RE relocations
on the parameter type.

Verified: uprobe programs now load as 992B/936B (not 16B), and the
demo-go app shows REAL-ALLOWED-KEY-12345 in httpbin.org response
headers (eBPF rewrite working end-to-end).
