feat: acquisition groups — one window per read, from the agent through .rez to the query engine (#1070)

Metrics are now grouped by when they were read. A group is one read section --
a BPF map read, a procfs file read, a sweep over like entities -- and the group
owns the acquisition window, not the individual metric. The rule is uniform:
one table == one group == one window.

That idea runs end to end. The agent stamps one window per group, SnapshotV3
carries groups on the wire, the recorder writes one .rez table per group with a
single window pair, and the query engine resolves table-level windows into
rate()/irate() uncertainty bounds.

Measured on a 32-core x86_64 host at 50ms over 300s, same agent, differing only
in snapshot_format: archives are 0.386x the size, rate queries run at 0.52-0.60x,
a cross-group union query at 0.49x, scrape wall time at 0.44x, agent CPU 0.59%
against 1.75%, RSS at parity. The archive result beats the synthetic gate's
0.63x prediction and the query results land inside its predicted band.

The win is scale-dependent and the reversal is recorded rather than hidden: at a
1s interval the same queries are 1.13-1.42x slower, because the fixed cost of
opening about twice as many tables stops being repaid by narrower reads. In
absolute terms 136-156ms against 110-122ms.

Landed config-gated -- [general] snapshot_format still defaults to "v2", so this
changes no default behavior. Flipping the default is a separate decision.

Verified beyond CI with a consumer smoke on Linux: V3 archives open in the viewer
in file and live-agent modes, cross-group union queries return data through the
viewer API, and hindsight buffers a V3 stream, stays readable live with unsealed
WAL rows, and captures a clean queryable snapshot with bands intact.
