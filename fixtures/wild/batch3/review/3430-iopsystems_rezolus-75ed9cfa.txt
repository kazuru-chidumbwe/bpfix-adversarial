feat(blockio): split latency into queue, device, and end-to-end phases (#1124)

* feat(blockio): expose queue residency, not just service latency

Closes #1054.

`blockio_latency` measured service time only, so a saturated device and a
merely busy one looked alike: in the reproducer on the issue, a victim
service's client-observed p99 went 55.8 ms -> 454 ms (8.1x) while
`blockio_latency` p99 did not move a single bucket. The delay was real and
being spent where the histogram never looked -- waiting in the queue.

The hooks were already there. `block_rq_insert` and `block_rq_issue` both
called `trace_rq_start`, writing one timestamp keyed by the request, so issue
simply overwrote insert's stamp and the insert->issue interval was discarded.
This keeps both stamps in one hash entry (`struct rq_stamps`) and records the
gap as `blockio_queue_latency`, split by op exactly like `blockio_latency`.
No new probe attach, so no principle-11 concern.

Semantics:

- Service latency is unchanged. Complete measures from the issue stamp when
  there is one and the insert stamp otherwise -- exactly the value it reported
  before, when issue overwrote insert.
- Requests that bypass the scheduler (blk-mq with the `none` elevator issues
  directly) have no queue phase. Their `insert` stays zero and nothing is
  recorded, rather than a fabricated zero wait.
- A requeue-then-reissue bills the original wait once: `insert` is cleared at
  the first issue.

Queue residency gets its OWN acquisition group. It is a different metric
family from service latency -- different phase, moves independently under
saturation -- and principle 18 keeps families in separate groups even when
read back-to-back. The four op classes within each family are like entities
and share their family's group, as before.

The dashboard gains a "Queue Wait" subgroup, gated on the metric actually
being present so recordings from older agents (and hosts whose requests never
queue) do not render empty plots.

`blockio_queue_latency` is not recoverable by prefix inference -- neither
`blockio_latency` nor `blockio_requests` is a `_`-boundary prefix of it -- so
it needs an explicit `METRIC_SAMPLERS` entry. Note that
`metric_samplers_match_agent_attribution` only catches this on Linux; on macOS
the non-Linux `stats.rs` include gives a module path that attributes to
`unattributed`, and the test skips.

Verified: both BPF targets compile (`clang -target bpf` against the checked-in
x86_64 and aarch64 vmlinux.h); insert 23 insns, issue 91, complete 75. Full
test suite and clippy clean. NOT verified here: runtime behaviour and the
measured per-refresh cost -- this is a macOS workstation, so no BPF load, no
fio reproducer, and no principle-16 number. Both need a Linux host before
merge.

* feat(blockio): split latency into queue, device, and end-to-end phases

Follows review on #1124 and the decision to rename rather than add alongside.

`blockio_latency` measured only the device phase, so a saturated device and a
merely busy one looked alike. It is renamed `blockio_device_latency` — the same
measurement, since the pre-split code let issue overwrite insert's stamp — and
joined by two new phases:

- `blockio_queue_latency` (insert -> issue), the component that grows under
  saturation while device latency stays flat.
- `blockio_total_latency` (insert -> complete), what the issuing workload
  actually experiences. Measured directly, not summed: two histograms cannot
  be added.

Readers treat the old and new device-latency names as one metric via
`blockio_device_latency_metric`, so existing recordings keep rendering. The web
dashboard and the TUI both call it rather than re-deriving the alias.

Adopted from prior WIP on the delta host, which had already made the naming
decision and solved two things well: the alias helper, and the TUI live-mode
subtlety that the store is empty at startup (`init_live_mode` only spawns
`ingest_loop`, which awaits its first tick), so anything derived from the metric
catalog must be recomputed each tick rather than once before the loop.

Review findings addressed:

- A leaked map entry could poison the new metrics. The pre-split code was
  self-healing — both start hooks did an unconditional update, so a stale stamp
  at a recycled `struct request *` was always overwritten before it was read.
  The split reads `insert` without writing it, so a leaked entry could surface
  as a multi-minute sample in exactly the histogram someone opens to diagnose
  saturation. A pointer key cannot distinguish stale from real, so
  `plausible_span()` bounds it: the block layer's own request timeout is 30s.
- `stamps->insert` is hoisted to a local; clang reloaded it after the
  `bpf_probe_read_kernel` inside `rq_op()`, so the guard did not cover the
  value actually subtracted.
- The Queue Wait rate came from `blockio_operations`, which counts *completed*
  requests — both a byte-identical duplicate of the Device plot and non-zero on
  a host where nothing queues. It now derives from the queue histogram itself.
- The dashboard gate is an agent-version gate and only that; `update_from` is
  called unconditionally every tick, so a collecting agent always publishes the
  series. Comment and docs corrected; they claimed it could detect whether
  requests actually queued.
- Added a positive dashboard test. The negative one alone could not tell
  "correctly gated out" from "the gate names a metric that never exists" — a
  typo would render the subgroups never and still pass.
- Filled in the surfaces the first cut missed: site/docs/telemetry.html,
  CHANGELOG, config/agent.toml.

Device-phase equivalence with the pre-split code was verified across every hook
ordering (insert only, issue only, insert->issue, requeue+reinsert, reissue
without reinsert, issue->insert, repeated inserts): `begin` equals the
last-written stamp in all of them, which is what makes the reader-side alias
sound.

Verified: both BPF targets compile against the checked-in x86_64 and aarch64
vmlinux.h; full test suite (676) and clippy clean.
