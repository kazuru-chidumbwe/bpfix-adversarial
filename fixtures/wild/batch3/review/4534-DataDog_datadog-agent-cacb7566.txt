[CWS-6628] Implement the unshare syscall event (#54609)

<!--Please give us some feedback on your experience writing this PR ! https://app.datadoghq.com/forms/43db4c02-6837-400c-8083-692e141b1b88 !-->

### What does this PR do?

Adds a public `unshare` CWS event carrying the requested namespace flags, so detection rules can match the syscall itself rather than the name of the calling binary:

```
unshare.flags & CLONE_NEWNET > 0
unshare.flags & (CLONE_NEWUSER | CLONE_NEWNET) > 0 && process.file.name != "docker"
```

New SECL surface: `unshare.flags` (bitmask, `Clone flags` constants) and `unshare.retval`. 12 `CLONE_*` constants are registered.

### Motivation

Jira: [CWS-6628](https://datadoghq.atlassian.net/browse/CWS-6628) (also filed as [CWS-6778](https://datadoghq.atlassian.net/browse/CWS-6778) — duplicates).

Requested by the detection guild. Recent Linux LPE exploits call `unshare` **directly** to create a new network namespace and thereby obtain `CAP_NET_ADMIN`. Today CWS can only catch this via `process.executable.name == "unshare"`, which misses every exploit that invokes the syscall from its own code.

> [!NOTE]
> The Jira description claims this complements an existing `setns` event. There is no `setns` instrumentation in CWS — `setns` appears only in the syscall-number tables used by the syscall-monitor event. This is CWS's first namespace-lifecycle event. Scope is unchanged; the ticket framing is just wrong.

### Describe how you validated your changes

The `syscall_tester` helper invokes `unshare(2)` **directly** rather than exec'ing `unshare(1)`, since catching direct syscall callers is the point.

### Additional Notes

<details>
<summary>Why the public event reuses event ordinal 46, and why that matters</summary>

`unshare` was already hooked, but narrowly: the hook bailed out unless `CLONE_NEWNS` was set, and the resulting `unshare_mntns` event was swallowed in userspace after registering the mount-namespace copy (`field:"-"`, never dispatched to rules).

That internal event fires **once per cloned mount** — `hook_make_visible`, `hook_attach_mnt`, `hook___attach_mnt`, `hook_attach_recursive_mnt` and `hook_propagate_mnt` each call `handle_new_mount()` for a distinct mount, which tail-calls through to `dr_mount_stage_two_callback` → `send_event`. Correct for mount bookkeeping; wrong for detection, where a rule must fire once per syscall.

So the two concerns are now separate event types:

- **`EVENT_UNSHARE` (ordinal 46, reusing the old slot)** — public, per-syscall. Full process/cgroup/span context plus the raw flags bitmask, sent once from the exit hook.
- **`EVENT_UNSHARE_MNTNS` (newly appended)** — internal, per-mount. Semantics unchanged, still consumed by `handleNewMount` and never dispatched to rules.

Keeping the *public* event at ordinal 46 is load-bearing. `probe_ebpf.go` packs enabled events as `1 << (eventType - 1)` into a **`uint64`**, mirrored kernel-side in `helpers/events.h`. `PivotRootEventType` is ordinal 64 — the last representable bit, which is exactly why `LastEventType = PivotRootEventType`. A newly appended public type would be ordinal 69 and therefore permanently unreachable by `is_event_enabled()` and by `applyDefaultFilterPolicies()`. The internal event doesn't care, since internal events are never gated by that mask.

</details>

<details>
<summary>Event volume</summary>

Bounded by a single gate: **`is_event_enabled(EVENT_UNSHARE)`** — no event at all when no loaded rule references `unshare.*`. Every `unshare` call is reported once that gate opens, so all 12 exposed `CLONE_*` constants are matchable and the `flags` field carries the full raw bitmask.

An earlier revision also filtered kernel-side on `CLONE_NEWUSER | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWPID`. That was dropped in review: it silently made rules on the other exposed constants (`CLONE_NEWUTS`, `CLONE_NEWIPC`, `CLONE_NEWTIME`, …) unable to fire. Per-flag volume control belongs in `unshare` approvers, as a follow-up.

`CLONE_NEWNS` is always *cached* regardless of the gate, because the mount resolver depends on that hook entry.

</details>

<details>
<summary>Known gap and follow-ups</summary>

- In `handle_new_mount` (`mount.h`), if the mount bookkeeping bails early it calls `pop_syscall()`, dropping the cache entry before the exit hook runs — so that particular `unshare(CLONE_NEWNS)` produces no public event. Narrow degraded path, mirrors existing behaviour, but a real coverage hole for `CLONE_NEWNS` specifically.
- ebpfless/ptracer support deferred, as `setrlimit` did.
- `setns` instrumentation (the join-side signal) not in scope.
- Four existing events (ordinals 65–68: `SampleRefresh`, `SetSid`, `Nop`, `Socket`) are already unreachable by the `enabled_events` mask and silently stay that way. Widening it past 64 bits is separate, cross-cutting work worth filing.

</details>
