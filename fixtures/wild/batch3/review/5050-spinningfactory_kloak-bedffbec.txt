feat: add OpenSSL 3.0-3.1 support (3-hop H extraction chain) (#141)

* feat: add OpenSSL 3.0-3.1 support (3-hop H extraction chain)

OpenSSL 3.0-3.1 uses a simpler pointer chain to reach the GHASH key:
SSL* → enc_write_ctx → algctx → H (3 hops, no record layer). OpenSSL
3.2+ uses SSL* → wrl → enc_ctx → algctx → H (4 hops via OSSL_RECORD_LAYER).

The 3-hop chain is signaled by WRLToEncCtx=0 in the offset table.
SSLToWRL then stores the enc_write_ctx offset instead. BPF checks
wrl_to_enc_ctx > 0 to choose the chain variant. The last two hops
(enc_ctx→algctx→H) are identical.

This unblocks Debian 12 (bookworm) containers which ship OpenSSL 3.0.x,
including the openclaw Node.js image (OpenSSL 3.0.19).

Known offsets (verified via pahole, identical on aarch64 and x86_64):
  3.0-3.1: enc_write_ctx=2168, enc_ctx_to_algctx=168, algctx_to_h=328

* fix: key xor_pending by tgid for cross-thread visibility (Node.js/libuv)

xor_pending was keyed by pid_tgid (thread-specific). Node.js/libuv
encrypts via SSL_write on one thread but writes to the socket on the
event loop thread — different pid, same tgid. The kprobe on tcp_sendmsg
never found the uprobe's xor_pending entry because the thread IDs
differed.

Fix: key by tgid (process ID, upper 32 bits of pid_tgid). All threads
in the same process share tgid, so the kprobe finds the entry regardless
of which thread does the socket write.

This is safe because xor_pending is created and consumed within the same
synchronous call chain (SSL_write → encrypt → socket write → kprobe).
No concurrent interleaving is possible:
- Node.js: single-threaded event loop
- Go: goroutine locked to OS thread during syscall, Conn.out.Mutex held
- Multi-threaded OpenSSL: different connections have different tokens

* feat: support memory BIO apps (Node.js) with multi-segment TLS records

Node.js and other memory BIO apps encrypt into memory buffers, not
sockets. The encrypted data reaches the kernel via writev, producing
multiple TCP segments per TLS record. This breaks the assumption that
tc_egress can see the full record in one skb.

Changes:
- Per-tgid tls_offset_config (HASH map) with global fallback (key=0),
  allowing different OpenSSL versions per process on the same node
- Version detection: prefer higher/more-specific version string,
  try main executable before shared libs (catches Node.js bundled OpenSSL)
- memory_bio flag in xor_pending: conditional write_seq and xor_pending
  deletion based on whether fd resolution succeeded (socket vs memory BIO)
- Multi-segment TLS records: remove bpf_skb_pull_data linearization,
  add tc_tag_pending map for deferred GHASH tag patching across segments
- SSLToVersion=72 for OpenSSL 3.5.x (ssl_connection_st.version offset)
- Fix xor_pending re-lookup using &tgid instead of &pid_tgid (line 2039)

Tested on EKS with: Node.js/OpenSSL 3.5.5 (openclaw → Gemini API),
curl/OpenSSL 3.5 (Alpine, 4-hop), curl/OpenSSL 3.0 (Debian, 3-hop),
Go crypto/tls (pg-consumer → PostgreSQL).

* fix: xor_pending TTL, SSLToVersion sentinel, numeric version compare, test curl wait

1. xor_pending TTL: for memory BIO apps, delete stale entries older than
   2s to bound kprobe overhead. The encrypt→writev gap is typically <10ms.

2. SSLToVersion sentinel: change from 0 to 0xFFFFFFFF so offset 0 is
   usable. OpenSSL 3.0 ssl_st.version is at offset 0 (verified via
   pahole). Enables correct nonce_len detection for 3.0/3.1.

3. versionBetter: numeric comparison via strconv.Atoi instead of
   lexicographic, handling future versions like 3.10 > 3.9 correctly.

4. E2E cipher test: wait for curl to be installed in Debian containers
   before starting uprobe readiness checks, eliminating "curl: not found"
   noise in CI logs.
