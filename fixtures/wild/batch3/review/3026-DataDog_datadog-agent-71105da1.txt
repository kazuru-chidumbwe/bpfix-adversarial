dyninst: any/all predicates over collections (#50722)




### What does this PR do?

Add any(coll, pred) and all(coll, pred) to the dyninst expression language for use in probe `when:` clauses. Supports slices, arrays, and Go 1.24+ swiss-table maps.

Inside the predicate body, the iteration variable is `@it`. For maps, `@it` is the current key (with `@key` as an accepted synonym) and `@value` is the current value — each its own loop variable anchored at a different offset in the per-iteration scratch slot, so a body like `{@key == "match" && @value == 42}` splits across the two without any synthetic struct.

The body's scope is closed: only `@it` (and `@key` / `@value` for maps) and literal constants may be referenced — outer-scope variables and nested any/all are rejected as typed Issues.

Iteration is capped at 4096 elements per call. Larger collections still short-circuit normally (the cap only matters if no short-circuit fires); when iteration exhausts the capped budget without a short-circuit result, the surrounding condition reports an eval error.

Null comparison on a member-access chain (e.g. `m.ptrField != null`, `@value != null` for a map of `*T`) preserves the pointer rather than auto-derefing it. The general resolveExpression path always auto-derefs trailing pointers to provide capture semantics, which would otherwise strip the byte the null comparison needs.

The lowering uses single-step `pc -=` back-jumps in the existing sm_loop rather than a nested bpf_loop, staying within the BPF verifier's call-depth budget. Collections stream from user memory one element at a time into a per-loop scratch slot; the collection itself never enters scratch. Iteration state lives on the SM struct, not the data stack, to keep verifier combined-stack usage low (especially for swiss-map walks, which use sm_swissmap_step_advance / sm_swissmap_read_current_slot helpers sharing state through swissmap_loop_state).

New stack-machine opcodes: ExprLoadAddress, {Array,Slice,SwissMap}Loop- {Begin,End}, ExprAdvanceOffset. Body-side faults (nil deref / OOB) call sm_return as usual, unwinding the enclosing condition with condition_eval_error armed — surfaced as a probe error in the event header.

### Motivation

These are useful and lay the groundwork for `contains` on slices and for `filter`
