Decode HTTP/2 headers in capture order (#3039)

* Decode HTTP/2 headers in capture order

HTTP/2 streams can complete in an order that differs from the order in
which their header blocks were observed. Decoding at completion can then
apply connection-scoped HPACK state in the wrong order.

Decode each direction when HEADERS are captured and retain bounded stream
metadata for completion. Mark decoder state unreliable whenever capture
loss, truncation, eviction, or bounded scanning makes its history
incomplete.

* Fix HTTP/2 CI regressions

Format the HTTP/2 transform and remove dead test code so both lint jobs accept the capture-order fix.

Allow the relay propagation test to recognize the fail-closed wildcard used when instrumentation attaches after an HPACK table is populated. Keep the assertion strict by accepting only the expected RPC name or the wildcard and by verifying every client-to-server parent link.

* Preserve HPACK state across coalesced data

Only coalesced frames that carry another HPACK block can desynchronize
the decoder. DATA frames after HEADERS now leave the active connection
state intact, while skipped HEADERS and PUSH_PROMISE frames still fail
closed.

Limit poisoning to the affected request or response direction. Cover
reused connections where DATA shares the initial capture.

* Preserve spans when HTTP/2 metadata is missing

Emit completed HTTP/2 spans with a wildcard operation when an observed
header block cannot produce trustworthy request metadata. Previously,
the completion path discarded those spans.

Restore relay span-count checks for both decoded and wildcard operation
names so the integration test detects future drops.
