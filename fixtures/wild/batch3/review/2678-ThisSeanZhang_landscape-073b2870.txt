ebpf: pass through ICMP in tproxy mode (#206)

In tproxy mode the ingress program treated ICMP/ICMPv6 as a tproxy
protocol and fell into handle_pkg(), where the TCP/UDP socket lookup
necessarily misses (there is no ICMP socket to sk_assign) and the packet
is dropped with TC_ACT_SHOT. As a result any device steered into a
tproxy container loses all ICMP: ping, traceroute and PMTU discovery
stop working, while TCP/UDP keep flowing.

Detect ICMP/ICMPv6 in tproxy_ingress and, instead of sk_assign, mark it
(0x2, avoiding the 0x1 bit consumed by the fwmark 0x1/0x1 lookup 100
tproxy rule), set PACKET_HOST and TC_ACT_OK so it is released to the
container routing stack (mirroring route_mode_ingress). Users forward it
out the WAN with their own nft/iptables rules.

The example redirect image's start.sh gains an ip_forward + MASQUERADE
rule for that mark so ICMP works out of the box; Dockerfile installs
iptables. TCP/UDP tproxy behaviour is unchanged.

Verified end-to-end on kernel 7.0: a LAN client steered into a
tproxy container can ping/HTTP a WAN host; ICMP egresses direct via WAN
(mark 0x2 MASQUERADE) while TCP is still proxied. Reverting the
eBPF change reproduces the 100% ICMP loss.
