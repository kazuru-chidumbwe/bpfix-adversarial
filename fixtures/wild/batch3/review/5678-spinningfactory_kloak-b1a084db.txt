* fix: validate kloak-enabled secrets at admission (close host-filter bypass)

The BPF host filter check `val_host_len < MAX_HOST_LEN` meant a 64-byte host
silently disabled filtering, allowing the secret to be rewritten on any wire
destination. The Go sync path was also truncating oversize values and short
values were only caught by the reconciler after admission — both surfaces
deferred problems to runtime or left them silent.

- sync.go: reject entries whose host ≥ 64 bytes instead of truncating; the
  secret stays on the shadow placeholder so the real value never leaks.
- pkg/webhook/secret_validator.go: new ValidatingAdmissionWebhook wired on
  Secrets with getkloak.io/enabled=true. Checks: hosts label (≤63 bytes,
  valid RFC 1123 DNS or "*"), port label (valid PORT or PORT/PROTO), data
  entries (8..128 bytes, non-empty). Failures surface at `kubectl apply`
  with a clear reason instead of showing up as "shadow not found" on pods.
- Helm chart: append ValidatingWebhookConfiguration reusing the same service
  and CA bundle as the mutating webhook. Scoped by objectSelector,
  failurePolicy: Fail.
- e2e: new secret_validation_test.go (11 cases) + helper tryCreateEnabledSecret
  that returns the API error. Updated TestShadowSecretLengthMatching to stay
  within [8, 128] and removed TestShadowSecretLengthTooShort (admission now
  catches the case before the reconciler sees it).

* fix: reject *.domain wildcard patterns (BPF filter is exact-match)

The BPF host filter (helpers.h: hosts_match) does byte-for-byte comparison,
so a literal "*.example.com" in the map would never match a real hostname
on the wire. Only the single-character literal "*" is meaningful (treated
as "skip host filter").

- Validator comment now documents the rule and points to the runtime.
- Happy-path e2e test no longer uses "*.internal.example.com" (would fail).
- New test RejectsWildcardSubdomain pins the behavior so a future change
  to allow globs must also relax the validator.

* fix: key go_tls_offset_config by (cgroup_id, exe_inode)

The Go H-extraction path was broken in nested container deployments (kind
nodes, k3d) because go_tls_offset_config was keyed by tgid. BPF's
bpf_get_current_pid_tgid() always returns root-NS PIDs, while kloak running
inside a kind-control-plane container sees only kind-NS PIDs. The two
never match, so every Go connection's H extraction hit "no offsets" and
bailed — no tls_conn_state populated, no tc_pending, no rewrite.

This also wires up three pre-existing but dead DBG_KPROBE_BRIDGE_*
counters and corrects debugCounterNames: it had stale entries from a
removed version of the C enum (tc_skip_reclen/load/store/nontls,
tc_no_tail/empty/no_entry) that were silently mislabeling the bridge
counters.

Fix: key by (cgroup_id, exe_inode). cgroup_id is a kernel-level ID
consistent across PID namespaces. exe_inode prevents collisions when
different binaries share a cgroup (e.g. a shell that execs a Go binary,
or one binary forking another) — without it, the last-pushed offsets
would overwrite earlier ones and corrupt TLS for the first binary.

- BPF: new struct go_tls_key { cgroup_id; exe_inode }; kprobe reads
  cgroup via bpf_get_current_cgroup_id and inode via BPF_CORE_READ on
  task->mm->exe_file->f_inode->i_ino.
- Go: pushGoTLSOffsets/AttachTLS now take cgroupID; stat(/proc/<pid>/exe)
  resolves the inode; push uses the generated tlsuprobeGoTlsKey type.
- UntrackCgroup iterates go_tls_offset_config and deletes any key whose
  cgroup_id matches, so pod teardown doesn't leak entries.
- UntrackTGID no longer touches go_tls_offset_config (it's not keyed
  by tgid any more).
- Missing DBG_KPROBE_BRIDGE / BRIDGE_NO_ENTRY / BRIDGE_H_FAIL dbg_inc
  calls are now in place — surface at top of the tcp_sendmsg kprobe,
  at each H-extraction early-return, and after a successful bridge.
- debug bpf_printk markers added under #ifdef KLOAK_DEBUG at each Go
  H-extraction failure site to narrow future debugging.

Verified end-to-end on kind (linuxkit 6.12 kernel): demo-go pod's
httpbin.org call rewrites the allowed secret on the wire and leaves
the blocked secret as the shadow placeholder.

* fix: apply (cgroup_id, exe_inode) keying to OpenSSL path + kind exec fixes

Follow-up to the Go fix in the same branch. Three related changes:

1. tls_offset_config (OpenSSL) now uses the same (cgroup_id, exe_inode)
   composite key as go_tls_offset_config. The previous PID-keyed map with
   a global key=0 fallback silently broke isolation between different
   OpenSSL versions on the same node (e.g. Node.js BoringSSL + system
   libssl) on nested deployments where userspace PIDs don't match BPF's
   root-NS PIDs. Drop the key=0 fallback entirely now that the lookup
   is namespace-safe. Both maps share one struct tls_binary_key.

2. setupCgroupAncestor now substring-matches "kubepods" instead of
   requiring exact "kubepods" / "kubepods.slice" names. On kind the
   directory is "kubelet-kubepods.slice" and the old code missed it,
   leaving cgroup_ancestor empty. With an empty ancestor,
   bpf_current_task_under_cgroup() returns !=1 for every task and the
   sched_process_exec tracepoint drops every event in BPF — which meant
   post-exec uprobe re-attach never ran (shells that exec into the real
   binary left kloak with offsets for the shell, not the app). Also
   anchors detection on /proc/self/cgroup so the found ancestor is
   guaranteed to be on the controller's own task chain.

3. The exec tracepoint handler was using event.Tgid (BPF's root-NS PID)
   to open /proc/<pid>/exe. In nested deployments the controller's /proc
   is a child namespace and can't see root-NS PIDs, so every re-attach
   failed with ENOENT. Resolve current PIDs via the tracked cgroup's
   cgroup.procs (which lists PIDs in the controller's own NS) and attach
   to each. This is a superset of what we need and is idempotent.

Verified end-to-end on kind:
- Go demo: allowed secret rewritten on wire, blocked stays as shadow
  (host-filter match behaves correctly).
- Python/OpenSSL demo: same. Shell entrypoint exec's python →
  tracepoint fires → kloak re-attaches with python's exe inode → next
  requests.get() rewrites the allowed secret.

* fix: per-cgroup OpenSSL offset fallback for short-lived processes

The composite (cgroup_id, exe_inode) key breaks when a process fires
SSL_write before the controller has pushed offsets for its specific
inode — e.g. `curl` spawned via `kubectl exec`, apt-get helpers during
container startup, or anything exec'd too briefly to race the push. The
old global key=0 fallback masked this; once removed, TestCipherSuites/3hop
timed out because the debian image fires curl from a fresh shell and the
per-binary push never caught up.

Fix: push a second entry at (cgroup_id, 0) carrying the same OpenSSL
offsets. BPF tries (cgroup_id, current_exe_inode) first and falls back
to (cgroup_id, 0). Safe because every process in a cgroup shares the
same libssl.so through the container's rootfs — one offset set is valid
for all of them.

Scoped to OpenSSL only. Go's map still requires an exact inode match:
statically-linked Go binaries can legitimately embed different
crypto/tls layouts, so a cgroup-wide fallback there would risk corrupting
TLS for whichever binary didn't push last. OpenSSL has no such concern.

UntrackCgroup's existing iterate-by-cgroup-id cleanup reaps the fallback
entry the same as any other key in that cgroup, so pod teardown stays
clean.

Verified on kind: debian:bookworm-slim with `kubectl exec sh -c "curl …"`
now sees the real secret on the wire — the pattern TestCipherSuites/3hop
exercises.
