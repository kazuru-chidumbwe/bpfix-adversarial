[CORE-13478] BPF: stop the connlimit recount charging host-origin traffic

The design doc says host-originated traffic is "neither counted nor limited" by
the QoS ingress connection limit. It is not limited; it was counted, so a
host-networked pod could exhaust a workload's ingress quota and lock out
pod-network clients.

At to-wep a local-host source takes goto skip_policy (tc.c:585), so the ingress
check never runs (tc.c:1463) -- no increment, no stamp. But conntrack_create
still makes an entry, and ConnLimitScanner.Check tallied it from the tuple and
opener bit alone, reading no flag.

Record the decision rather than inferring it: to-wep sets CALI_ST_HOST_ORIGIN
where it identifies the local-host source, CT-create stamps
CALI_CT_FLAG_HOST_ORIGIN from that flag, and the recount skips those entries,
so counting and enforcement cannot drift apart. Not gated on
INGRESS_CONN_LIMIT_CONFIGURED, so a limit added later still finds the
connection marked. Flags reuse existing bytes: no map version bump.

FV measurement either side of this commit, same workload:

    3 host-origin connections admitted against limit 2   (unchanged)
    ingress count with 2 host-origin connections held: 2 -> 0

Three simpler discriminators were rejected. Inferring from the opener leg
(Ifindex == 0 && !Workload) is unsound both ways: conntrack.h:1207 rewrites the
opener ifindex for lo and bpfout.cali, while traffic ingressing an interface
with no BPF program gets ifindex 0 yet is legitimately limited -- exempting it
would under-count, which fails open. Gating on CALI_CT_FLAG_CONNLIMIT_INGRESS
is also unsound: it is stamped only inside if (cv) at tc.c:1487, so a genuine
first ingress SYN is incremented and never stamped. Reusing
CALI_ST_SKIP_POLICY is unsound for the same reason as the first: skip_policy:
is a shared label reached from seven paths, and the ICMPv6 allow (tc.c:806) and
the pre-NAT path (tc.c:492) are not HEP-gated, so to-wep flows that are not
host-origin would be exempted from the recount.

current_count is still written unclamped -- a count above max_connections is a
true signal that something is miscounting, and clamping would have hidden this.

Tests, on top of the repro in the previous commit: the scanner test keys on the
flag and its siblings become the guard that unflagged entries still count; the
BPF unit test asserts the admitted SYN carries HOST_ORIGIN; an nftables control
asserts the behaviour BPF now matches, passing unchanged either side. The drain
spec moves to pod-origin connections, which are still counted, and starts its
clock before the close -- closing twenty connections outlasted the interval
being measured. It reports 2.5s, against the ~60s in QOS-15, which was the old
connLimitScannerRunEveryN = 3 downsampling.

Verified: ut-bpf 2216/0 failures; fv-bpf host-origin 12/12; fv-bpf "With
connection limits" 64/64; fv-nft control 2/2.
