feat(ebpf): H capture at libcrypto cipher init for OpenSSL (closes #175 for OpenSSL) (#188)

* feat(ebpf): capture GHASH H at libcrypto cipher init for OpenSSL

Closes #175 for OpenSSL processes (curl, python, ruby, ...). Node.js /
BoringSSL stays on the existing kprobe-walks-chain path unchanged — it
will get its own EVP_AEAD_CTX_new hook in a follow-up PR.

## Why

PR #187 attempted to move the H chain walk from the tcp_sendmsg kprobe
to the SSL_write entry uprobe. That worked for libssl 3.0/3.1 (3hop)
but failed consistently for libssl 3.5.6 (4hop): counter dump showed
xor_conn_check=4167 with xor_conn_hit=0 — the SSL → wrl → enc_ctx walk
returned null at one of the hops every time. The hypothesis (not
verified by source-reading but consistent with all observed counter
patterns) is that libssl 3.5+'s record-layer rework populates
wrl→enc_ctx lazily during the encrypt step inside SSL_write. SSL_write
entry is too early; the kprobe at tcp_sendmsg ran *after* the encrypt
setup and that's why pre-PR-187 worked.

The fix is to capture H at the canonical moment OpenSSL keys the
cipher — EVP_CipherInit_ex / EVP_CipherInit_ex2. By the time the
uretprobe fires, the EVP_CIPHER_CTX is fully populated. We cache by
(tgid, EVP_CIPHER_CTX *). At SSL_write time h_extract walks
SSL → wrl → enc_ctx (still has the lazy-init issue, but only for the
hops that resolve quickly in practice — see "Risks" below) and looks H
up by enc_ctx pointer.

## What changes

### BPF C (pkg/ebpf/bpf/tls_uprobe.c)

- New `evp_h_cache` LRU hash keyed by (tgid, EVP_CIPHER_CTX *), value
  carries 16-byte ghash_h, cipher_type, nonce_len.
- New `evp_init_scratch` HASH keyed by pid_tgid for entry → uretprobe
  argument bridging (uretprobe doesn't see args directly).
- New `tls_strategy` HASH keyed by tgid: 0=KPROBE_WALK (default,
  BoringSSL/static), 1=LIBCRYPTO_HOOK (controller wrote it after the
  EVP_CipherInit attach succeeded for this pid's libcrypto.so).
- New `bpf_uprobe_evp_cipher_init` + `bpf_uretprobe_evp_cipher_init`:
  capture EVP_CIPHER_CTX *, walk evp_ctx → algctx → H using existing
  offsets, byte-swap, store in evp_h_cache. Filters non-GCM ciphers
  via the H==0 check (algctx → H is only valid for AEAD GCM contexts).
- `bpf_h_extract` refactored: walks SSL → wrl → enc_ctx (no further
  hops), looks up evp_h_cache by enc_ctx ptr. Reads nonce_len from
  SSL_CONNECTION.version. Falls through silently on cache miss.
- `bpf_uprobe_ssl_write` reads tls_strategy and tail-calls slot 2
  (h_extract) for LIBCRYPTO_HOOK, slot 1 (xor_path) for everyone else.
  The default branch is byte-for-byte the pre-PR-187 wiring.
- `bpf_xor_path` mi==0 init copies H from tls_conn_state into
  staged_pending so the kprobe can read it without a second lookup.
- `bpf_kprobe_tcp_sendmsg` else-branch: hot path is
  pending->h_valid==1 → memcpy from pending; cold path is
  pending->h_valid==0 → walk SSL → wrl → enc_ctx → algctx → H exactly
  like main today. The chain walk is preserved for BoringSSL and
  OpenSSL cold-start — neither claim is "papering over" since the
  walk is the only mechanism that works for those.
- New DBG_ entries: evp_init_entry, evp_init_h_ok, evp_init_h_zero,
  evp_init_chain_fail, h_extract_cache_hit, h_extract_cache_miss,
  kprobe_bridge_from_pending, kprobe_walk_legacy.

### Go (pkg/ebpf/uprobe.go)

- `attachLibcryptoCipherInit`: walks containerLibs, finds libcrypto.so,
  tries EVP_CipherInit_ex2 first (3.0+), falls back to
  EVP_CipherInit_ex (1.1+). Attaches entry + uretprobe pair. Stops at
  first symbol that resolves so we don't double-fire on _ex / _ex2.
- After successful libssl attach, calls attachLibcryptoCipherInit. If
  it returns true, writes `tls_strategy[tgid] = LIBCRYPTO_HOOK`.
  Otherwise the process stays on default = KPROBE_WALK.
- `UntrackTGID` cleans up `tls_strategy[tgid]` on process exit.
- `debugCounterNames` extended to match the new DBG_ enum entries.

## Verification matrix

- 3hop tests (TestCipherSuites/3hop): must remain at 100 % — the
  SSL → enc_write_ctx walk in h_extract still works and the cache
  lookup path covers it.
- 4hop tests (TestCipherSuites/4hop): expected to reach 100 % — H is
  now captured at cipher init, sidestepping the lazy-init problem.
- Python test (TestEBPFSecretRewrite/python): same code path as 4hop
  curl through libcrypto hook; expected pass.
- Go test: unchanged, must remain at 100 %.
- JS test (BoringSSL): expected to be at-least-as-good as current main.
  Node.js doesn't have libcrypto.so — process stays on KPROBE_WALK,
  which is the same flow that's been shipping. Follow-up PR adds the
  BoringSSL hook.

Counter pattern to watch:
- evp_init_entry > 0: cipher init hooks firing.
- evp_init_h_ok ~= evp_init_entry: AEAD-GCM contexts dominate.
- h_extract_cache_hit ~= xor_conn_check (for OpenSSL cgroups): cache
  is doing its job.
- kprobe_walk_legacy growing only for BoringSSL traffic, near-zero
  for OpenSSL. Significant kprobe_walk_legacy on OpenSSL traffic
  would mean libcrypto attach is failing — diagnostic signal.

## Risks

1. OpenSSL cold start (handshake before kloak attached) → cache miss
   → SSL_write skips patching. Same observable behavior as today's
   misses, different cause. Pod restarts after kloak handshake fresh.
2. EVP_CipherInit_ex symbol absence (statically-linked BoringSSL) →
   no attach, strategy stays at 0 (KPROBE_WALK), behavior unchanged.
3. Non-GCM ciphers fire our hook too — filtered by H==0 check. New
   evp_init_h_zero counter monitors. May want explicit cipher-NID
   filtering as follow-up if this proves noisy.
4. EVP_CIPHER_CTX_reset (TLS 1.3 KeyUpdate): hook fires again with
   same evp_ctx_ptr → cache update overwrites old H. Correct.
5. Strategy-flag race: very early SSL_write before the controller
   wrote tls_strategy[tgid] goes through KPROBE_WALK (legacy path).
   Acceptable — same behavior as main today.

## Out of scope (follow-ups)

- BoringSSL via EVP_AEAD_CTX_new for Node.js.
- Cleanup of tls_conn_state.wrl_ptr field (no longer carries useful
  info on the LIBCRYPTO_HOOK path).
- Explicit cipher-NID filtering in the cipher_init uretprobe (only if
  evp_init_h_zero proves noisy in production).

* fix(ebpf): hook EVP_CipherInit_ex (not just _ex2) — OpenSSL TLS uses _ex

PR #188's first run was a no-op behaviorally: the libcrypto attach
succeeded for EVP_CipherInit_ex2, but evp_init_entry stayed at zero.
The attach was right, but the symbol was wrong.

OpenSSL 3.x's TLS layer (ssl/t1_enc.c::tls1_change_cipher_state_cipher
for TLS 1.2 and ssl/tls13_enc.c::tls13_set_encdec_state for TLS 1.3)
keys the per-record cipher with EVP_CipherInit_ex, not _ex2. Both
symbols are public API entry points; neither wraps the other (both
call the static evp_cipher_init_internal directly). My previous
"break after first success" was based on the wrong assumption that _ex
was a thin wrapper around _ex2.

Hook both symbols. Double-attach is safe because the cache write is
idempotent for the same EVP_CIPHER_CTX * (same H, same offsets, same
algorithm). Comment updated to reflect the actual relationship.

Verified locally: nm -D /usr/lib/x86_64-linux-gnu/libcrypto.so.3 in
the demo-python-raw-tls image shows both
  T EVP_CipherInit_ex  @@OPENSSL_3.0.0
  T EVP_CipherInit_ex2 @@OPENSSL_3.0.0
as separate exported functions at distinct addresses.
