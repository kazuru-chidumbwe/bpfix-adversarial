dyninst: emit synthetic returns for panic-unwound probed frames (#50714)

### What does this PR do?

Detects when a probed Go function exits via `panic`+`recover` (instead of returning normally) and emits synthetic "return" events for the unwound frames, so they're finalized and reported instead of leaking indefinitely as in-progress entries.

irgen splices an internal probe attached to `runtime.recovery` into the IR program when at least one user probe targets a function. It runs through the standard `probe_run` → `sm_run` → `sm_loop` pipeline with a synthesised `@exception` capture expression bookended by two new stack-machine opcodes:

- `SM_OP_PANIC_UNWIND_PREPARE` reads `g._panic.{startSP,sp,recovered,goexit,arg}` via DWARF offsets, validates the panic chain, and writes `panic_lo_depth` / `panic_hi_depth` / `goid` into the event header.
- `SM_OP_PANIC_UNWIND_EVICT_SLOTS` walks `in_progress_calls[goid]` and zeroes every slot whose depth lies in `(lo, hi]`; deletes the map entry if empty.

The `@exception` capture reads `gp._panic.arg` (a 16-byte `runtime.eface`) and flows through `PROCESS_GO_EMPTY_INTERFACE` + `CHASE_POINTERS`, so the panic value renders as a typed Go value rather than a raw type pointer. One BPF event per recovery fans out across every matching in-flight invocation via `Buffer.NotePanicUnwoundRange` + a refcounted `SharedMessage` wrapper.

New `RuntimeStats` counters expose handler health: `RecoveryFires`, `RecoveryEvictedFrames`, `RecoverySubmitFailures`, `RecoveryNoOpenCalls`, `RecoveryFilteredGoexit`, `RecoveryInvalidState`. The recovery counters live in `stats_buf` slot 0 (the buffer is a shared ARRAY keyed by probe id; recovery counters are process-wide, not per-probe) and are written with `__sync_fetch_and_add`.

### Motivation

Before this change, when a probed function exited via `panic`, its `in_progress_calls` slot in BPF and its `bufferedEvent` in userspace were never reclaimed — the entry capture sat around until the buffer filled or the goroutine ID was reused. Users saw no return event and no diagnostic for the call. Both sides now get cleaned up promptly, and the user sees the entry capture plus a clear `"function did not return: panic was recovered by an ancestor frame"` evaluation error with the panic value rendered as the Return capture.

### Follow-up commit: review feedback

The second commit, `dyninst: address review feedback on panic-recover`, collects the changes that emerged from review. It bundles several distinct fixes:

- **`SharedMessage` refcount race.** The original `ReleaseBase()` unconditionally released the underlying dispatcher message, and sink.go gated the call on `len(readys)==0` — but a range-scan match can acquire a handle even when its `bufferedEvent` cannot finalize yet (entry side still in flight), so the handle would alias a sync.Pool-recycled `*ringbuf.Record`. Switched `SharedMessage` to a constructor-holds-base-ref pattern: `NewSharedMessage` takes one reference, `ReleaseBase` decrements it, and whichever caller performs the final decrement releases the underlying. Acquire and handle Release can interleave with ReleaseBase freely.
- **Submit-failure leak for panic-unwound events.** `SM_OP_PANIC_UNWIND_EVICT_SLOTS` evicts `in_progress_calls` slots before the final ringbuf submit. If the submit failed, the existing failure branches had no path for the recovery probe and the matching userspace `bufferedEvent`s leaked until budget/time eviction. Added `DROP_REASON_PANIC_UNWOUND_LOST` (carrying `goid`, `panic_lo_depth`, `panic_hi_depth`) and a new buffer method `NotePanicUnwoundRangeLost` that scans the tree and emits each matching invocation as a truncated panic-unwound capture. Hoisted the recovery-probe detection to the top of both submit-failure sites in `event.c` so the partial-fragment semantics of `PARTIAL_ENTRY` never apply to the recovery probe.
- **Budget eviction during fanout.** `chargeForFragment`'s single `excludeKey` could evict any of the other matches during a panic-unwound fanout, leaving the per-match mutation loop dereferencing dangling pointers. `NotePanicUnwoundRange` now pins every attaching match with a single upfront charge via a new `chargeExcluding` helper that takes a predicate. The pin set is a Buffer-resident scratch map cleared via `defer` to avoid per-call allocation.
- **Circuit-breaker for the recovery probe.** The recovery probe is irgen-synthesised and lives outside the user-configured probe set, so the existing breaker's `circuitBrokenProbes` filter couldn't suppress it on recompile. Added `irgen.WithSkipRuntimeRecoveryProbe` and an `actuator.LoadOptions.SkipRuntimeRecoveryProbe` flag wired through `runtime_impl`. When the breaker trips the recovery probe, the next recompile builds a program without it (recovery stays disabled for the process lifetime, matching pre-PR behaviour). User-facing diagnostics are suppressed for the synthetic probe.
- **Atomic recovery counters.** `stats_buf` is a shared ARRAY (not PERCPU); the existing hit/cpu counters use `__sync_fetch_and_add`. Converted the new `recovery_*` counters in `event.c` and `stack_machine.h` to the same atomics so concurrent recovery firings on different CPUs don't lose increments.
- **DWARF gating.** `synthesizeRecoveryProbeEventRoot` now requires `runtime._panic.{startSP, sp}` fields in DWARF; without both the BPF handler would degenerate to a `sp == start_sp == 0` coincidence to bail. Defense in depth: `sm_panic_unwind_prepare` bails explicitly when either offset is 0.

### Describe how you validated your changes

- New `panic_recover` testprog at `pkg/dyninst/testprogs/progs/panic_recover/main.go` covers six scenarios: a panic crossing an intermediate frame, `recover()` with no panic in flight, error-typed panic value, an unprobed frame between the panicker and the recoverer, panic+recover inside a probed-frame goroutine, and panic+recover in an unprobed-only goroutine.
- `pkg/dyninst/recovery_metrics_test.go` runs the testprog end-to-end and asserts the BPF stat counters match the scenario expectations.
- 11 new decoded-output fixtures pin the per-function expected captures and eval-errors.
- New unit tests in `pkg/dyninst/eventbuf/buffer_test.go` cover deferred-finalize, mixed-finalize, no-eviction-of-matches, and the `NotePanicUnwoundRangeLost` paths (single/multi-frame, goid boundary, no-matches, deferred-finalize, skip-when-real-return-present).
- New snapshot test `pkg/dyninst/actuator/testdata/snapshot/circuit_breaker_runtime_recovery_trip.yaml` exercises the full circuit-breaker trip → detach → recompile-without-recovery cycle.
- New focused test `pkg/dyninst/module/report_probe_error_test.go` verifies the kind filter on `ReportProbeError`.
- Snapshot fixtures regenerated to reflect the additional probe per program and `runtime._panic` entering the type catalog.
- Verified across all four Go toolchain versions on amd64 (arm64 builds; integration tests skipped per existing convention).
- `bazel build //pkg/dyninst/...` and `bazel test //pkg/dyninst/...` pass.

### Additional Notes

The `panic_recover` testprog uses `fmt.Errorf` (heap-allocated) rather than string-literal panics: `.rodata` pages aren't guaranteed resident at BPF read time, and `bpf_probe_read_user` returns `-EFAULT` for non-resident pages, which made the rendered value Go-version-dependent.

Note also that this doesn't let you use `@exception` in an expression, that's left as future work.

Multi-fragment recovery payloads (large interface{} panic values that span ringbuf flushes) are tolerated as a graceful degradation: `scratch_buf_flush_and_continue` does not preserve `panic_lo_depth`/`panic_hi_depth` across continuation headers, so fragments 1+ arrive at the sink with a zero range, match no invocations in `NotePanicUnwoundRange`, and are silently dropped. Fragment 0 already attaches the panic value to every match — the user sees a truncated single-fragment view in the rare large-payload case, and BPF eviction still happens correctly.
