fix(secrets): bit-exact shadow generator closes HTTP/2 HPACK padding bug (#233)

* test(e2e): regression test for HTTP/2 HPACK over-padding bug

The BPF map sync in pkg/ebpf/sync.go pads the Huffman-encoded real
value with 0xFF (EOS bits) until it matches the shadow's Huffman
length. RFC 7541 §5.2 only allows up to 7 bits of trailing 1s as
padding; anything longer MUST be treated as a decoding error. When
the shadow's Huffman density exceeds the real's by more than one
byte (typical when the real is mostly lowercase letters and the
shadow is Crockford Base32 uppercase + digits), the padding becomes
illegal and strict HPACK decoders (nghttp2, AWS ALB) drop the stream.

Existing coverage misses this:
  - TestEBPFSecretRewrite's real/shadow Huffman lengths happen to
    differ by ≤1 byte (legal 7-bit padding), so the bug stays latent.
  - demo-python (requests) and demo-js (node http) default to
    HTTP/1.1 — no HPACK in their path.
  - demo-go-boring explicitly forces HTTP/1.1 (ForceAttemptHTTP2=
    false), almost certainly to dodge this exact issue; no
    HTTP/2 + non-Go-stdlib-TLS coverage remains.

This commit adds TestEBPFHttp2HpackOverPadding which exercises
demo-go (HTTP/2 via ALPN against httpbin.org) with a low-Huffman-
density real value ("lowercase-secret-triggering-hpack-bug", 37
chars, HuffmanLen=26). The generated shadow's HuffmanLen lands at
~31 bytes — a 5-byte (40-bit) gap, well past the RFC's 7-bit
allowance. Without a fix, httpbin's HPACK decoder rejects the
header block and the demo never echoes the real secret back.

The test is t.Skip'd with a clear TODO and a list of candidate
fixes (tighten the shadow generator's Huffman invariant; rewrite
the HPACK length prefix in BPF; per-secret fail-open with WARN +
metric). Removing the Skip is the verification step for whichever
fix lands.

* refactor(secrets): ShadowGenerator takes Huffman length, not cleartext

generateShadowValue and ShadowGenerator.Generate previously took both
the cleartext real secret and its byte length as separate parameters.
The cleartext was used for exactly one thing — computing
hpack.HuffmanEncodeLength(realSecret) — and originalLen was always
len(realSecret) at every call site (verified across pkg/controller
and pkg/secrets/yaml). Two consequences:

  1. The two parameters were vestigial: every caller passed
     (len(real), real), so an accidental mismatch would silently
     produce a shadow of the wrong plaintext length and corrupt the
     in-kernel rewrite buffer.

  2. The cleartext entered pkg/secrets's shadow-generation code path
     even though the algorithm only needs a length target. Any future
     debug log, panic dump, or error format string inside this package
     could inadvertently surface the real secret.

Change the signature to take originalLen + realHuffmanLen and push the
HPACK length computation up to the two callers (pkg/controller and
pkg/secrets/yaml). The cleartext now never enters pkg/secrets.shadow's
scope. Test fixtures updated to call hpack.HuffmanEncodeLength locally.

No behavior change: same algorithm, same invariant guarantees, same
ErrHuffmanInvariantUnsatisfiable contract. Verified by the existing
pkg/secrets, pkg/secrets/yaml, and pkg/controller test suites.

* fix(secrets): bit-exact byte-by-byte shadow construction

Replaces the random-then-tune shadow algorithm with byte-by-byte
construction against an exact (originalLen, realHuffmanBits) budget.
Every shadow now satisfies len(huffShadow_bits) == realHuffmanBits
exactly, which means the encoded wire byte count matches the real's
exactly, which means the BPF map sync in pkg/ebpf/sync.go rewrites the
HPACK slot byte-for-byte with zero EOS padding regardless of the
real's character class.

This closes the HTTP/2 HPACK over-padding bug demonstrated by
TestEBPFHttp2HpackOverPadding: low-Huffman-density reals (lowercase +
dashes) previously produced shadows whose Huffman length exceeded the
real's by more than 7 bits — the sync path filled the gap with 0xFF
EOS bytes, violating RFC 7541 §5.2's "padding strictly longer than 7
bits MUST be treated as a decoding error" and triggering stream
resets from strict HPACK decoders (nghttp2, AWS ALB fronting
httpbin.org).

Algorithm (pkg/secrets/shadow.go):

  - Bucket every alphanumeric ASCII byte by its HPACK Huffman bit
    length into huffmanBuckets[5..7] (alphabet limits the per-byte
    code length to [MinBits, MaxBits]).
  - On each generation: tailLen = originalLen - len(ValuePrefix),
    tailBits = realHuffmanBits - prefixHuffmanBits.
  - Feasibility: pre-check tailBits ∈ [tailLen*MinBits, tailLen*MaxBits]
    in a single comparison. Returns ErrHuffmanInvariantUnsatisfiable
    immediately on the unreachable cases, with no randomness consumed
    on the error path (no timing oracle on realHuffmanBits beyond the
    feasibility predicate itself).
  - Per byte: pick code length k ∈ [lo, hi] uniformly where the
    [lo, hi] window is the intersection of [MinBits, MaxBits] and the
    bit budget remaining feasibility for the suffix. Then uniformly
    pick a byte from huffmanBuckets[k]. Two CSPRNG draws per byte;
    control flow does not branch on realHuffmanBits's value.

Side benefits beyond closing the bug:

  - Catches the previously-unhandled `shadowBits > realBits` case
    (old code's tuning loop only ran in the < direction; an
    unfortunately-dense ULID could overshoot a low-density real
    silently).
  - Removes the timing oracle on realHuffmanBits — the old code's
    tuning loop iterated `realHuffLen - initialShadowHuffLen` times,
    giving direct timing access to the real's encoded length.
  - Drops the github.com/oklog/ulid/v2 dependency — the new algorithm
    doesn't need timestamp-ordered shadows; pure CSPRNG with prefix
    collision retry is sufficient.

Public API:

  - Generate(originalLen, realHuffmanBits int, ownerID string,
    maxRetries int) — realHuffmanBits is now an exact bit count, not
    a byte count. Callers compute it via secrets.HuffmanBits(real)
    (added in pkg/secrets/huffman.go).
  - HuffmanBits(s string) int — bit-exact sibling of
    hpack.HuffmanEncodeLength (which rounds up to bytes).

Test-fixture updates:

  - Test reals using single/triple-char values ("v", "vvv", "abc",
    "abcd", "real-val", "real-dual", "aaa") were updated to feasible
    fixtures. The previous algorithm tolerated infeasible fixtures by
    silently producing wrong-length or invariant-violating shadows;
    the new algorithm rejects them cleanly with
    ErrHuffmanInvariantUnsatisfiable. This is a behavior tightening,
    not a regression — production secrets are ≥8 chars in practice.

* feat(secrets): shorten shadow prefix from "kloak:" to "kl::"

Drops the literal shadow prefix from 6 bytes (37 HPACK Huffman bits) to
4 bytes (27 bits). This widens the byte-by-byte shadow generator's
feasibility window from `[5N+7, 7N−5]` to `[5N+7, 7N−1]` total Huffman
bits, which translates to dramatically better coverage at small N:

  Length 8:  upper density 6.375 b/B → 6.875 b/B
  Length 21: upper density 6.762 → 6.952
  Length 40: upper density 6.875 → 6.975

Equivalently, the *minimum supported shadow length* for the same upper
density bound drops by ~5×: where the old prefix needed N=40 to cover
the density range `kl::`@N=8 reaches, the new prefix gives that
coverage out of the box at N=8.

This closes the remaining CI fixture failures from the previous
commit (`SECRET-8`, `BLOCKED8`, `REAL-BLOCKED-PORT-KEY`,
`BLOCKE-42B-...`) — they all sat just above the old window's upper
bound at their respective lengths and now slot comfortably inside.

eBPF matcher updates (pkg/ebpf/bpf/helpers.h):

  is_kloak_prefix:        6-byte literal "kloak:"           → 4-byte "kl::"
  is_kloak_prefix_huffman: 4 stable Huffman bytes
                          (0xeb 0x41 0xc7 0xd6)             → 3 stable bytes
                                                              (0xeb 0x45 0xcb)

The Huffman matcher drops one stable byte (32-bit → 24-bit pattern),
trading ~256× more BPF prescan-trigger candidates for the bit-budget
headroom. The 8-byte `secret_map` lookup confirms genuine matches, so
the extra prescan hits cost a few hundred nanoseconds each — negligible
under realistic traffic loads.

Coverage of common secret formats (1000-sample feasibility rate with
the new prefix):

  openssl rand -hex N=16:  98% feasible (was 51% with kloak:)
  openssl rand -hex N=20:  >99.8%       (was 88%)
  openssl rand -hex N=32:  100%
  openssl rand -base64 N=16:  98%
  openssl rand -base64 N=32:  >99.8%
  JWTs (any realistic size):  100%

* feat(webhook): fail-closed on Huffman-infeasible secrets at admission

real value has a Huffman bit count outside the achievable shadow
window for its length, the validating admission webhook now denies
the Secret at apply time. This matches the explicit product
preference — a kloak-labeled Secret that can't be safely shadowed for
HTTP/2 should NOT be silently accepted as HTTP/1.1-only. Users get
immediate `kubectl apply` feedback instead of discovering at runtime
that a credential is leaking unprotected through HTTP/2 paths.

* feat(secrets): widen shadow tail alphabet to MaxBits=8

Expands the byte-by-byte shadow construction's per-byte ceiling from
7 to 8 bits, lifting the feasibility window's upper bound from
`7N − 1` to `8N − 5` bits at any shadow length N. The lower bound
stays put at `5N + 7` — HPACK's 5-bit code-length floor is the
absolute global minimum and no alphabet change can reach lower.

What gets covered now (previously rejected at the ceiling):

  | Real value                                  | Bits | N=N window before  | window now      |
  | ------------------------------------------- | ---- | ------------------ | --------------- |
  | "SECRET-8" / "BLOCKED8"                     | 54/55| [47, 55]           | [47, 59]        |
  | "BLOCKE-42B-FGHIJKLMNOPQRSTUVWXYZ..."       | 290  | [217, 289] (-1)    | [217, 331]      |
  | "REAL-BLOCKED-PORT-KEY"                     | 143  | [112, 142] (-1)    | [112, 163]      |
  | strings.Repeat("x", 128)                    | 896  | [647, 895] (-1)    | [647, 1019]     |

Pure-lowercase reals like `strings.Repeat("a", 32)` still correctly
fail — they sit below the unfixable 5-bit floor and the admission
webhook rejects them at apply time via secrets.CanShadow.

bucket[8] population: the two natural 8-bit ASCII alphanumerics
('X', 'Z') plus four 8-bit punctuation chars ('&', '*', ',', ';'),
chosen so the upper bucket has 6 candidates rather than 2 — keeps
per-byte sampling entropy reasonable. Shadows may now contain those
punctuation chars in their tail (e.g. "kl::aB&cD*1"); still scannable
as kloak placeholders in logs.

Held the line at MaxBits=8 rather than pushing higher (10, 15, full
HPACK). Past 8 bits, the alphabet bleeds into rarely-used punctuation
('!', '"', '(', ')', '?' at 10 bits; '<', '{' at 15 bits) and the
shadows look increasingly weird for diminishing real-world coverage
gains — the practical population of secrets denser than 8 bits/byte
is just binary blobs, which need a fundamentally different rewrite
strategy (HPACK length-prefix manipulation + TLS record resizing).

Verified: pkg/secrets, pkg/webhook unit tests green; the boundary
test in TestGenerateShadowValue_UnsatisfiableReturnsError stays
correctly classified — X×16 needs 8.42 bits/byte, still above the
new MaxBits=8 ceiling by 5 bits.

* fix(secrets): scrub value-derived bit count from admission errors

CanShadow's error message previously included `target Huffman bits=%d`
— that count is computed directly from the real secret's bytes
(sum of per-byte HPACK code lengths) and the webhook surfaces this
error verbatim in both the admission denial (returned to the kubectl
caller and captured in apiserver audit logs) AND a structured
controller log via Warnw. Two leak paths a security-conscious
operator wouldn't want.

The Huffman bit count is a weak side channel — many distinct
secrets share the same bit count, so reversing the content from it
is infeasible — but it's still a function of the value, and a
security product has no business including value-derived statistics
in error paths that the caller doesn't already have access to the
value through. Strip it.

Replacement error split into two directional variants for
diagnostic clarity:

  too low:   density below achievable floor (e.g. all-lowercase real)
  too high:  density above achievable ceiling (e.g. binary blob)

Both messages name only the originalLen and the achievable bit
range, both of which are invariants the caller already knows (they
constructed the secret; the algorithm parameters are public). Users
get actionable diagnostics — "your secret is too low/high density
at length N, achievable range A–B bits" — without exposing any
statistic of the value's content distribution.

Surrounding webhook wrapping ("data[%q]: %w (value's HPACK Huffman
density is outside the range kloak can shadow…)") simplified to
just "data[%q]: %w" since CanShadow's new message is already
user-facing and self-contained.

Test fixture for "infeasible density rejected" updated to assert
the new "Huffman density is too low" substring; semantics unchanged
(the same value is still rejected, just with a leak-free message).

Verified: go vet ./..., go test ./..., golangci-lint run ./... —
all green.
