fix(ebpf): per-binary wbio offset — OpenSSL 3.0/3.1 silently broke on hardcoded 88 (#222)

`ssl_read_fd` in the BPF data plane reads SSL → wbio → BIO.num to recover
the socket fd, then looks it up in conn_ip_map to confirm a client-mode
connection set by connect(). The wbio offset was hardcoded to 88, which
matches `ssl_connection_st.wbio` on OpenSSL 3.2+ but is wrong on 3.0/3.1
where `struct ssl_st` puts wbio at offset 24.

Effect on every 3.0/3.1 caller (Ubuntu 22.04/24.04's stock libssl3,
Debian bookworm, RHEL 9.x): the uprobe reads garbage as the wbio
pointer, dereferences for BIO.num, returns a nonsense fd; conn_ip_map
miss trips the "skip server-mode SSL" guard in bpf_uprobe_ssl_write,
which returns 0 before writing to xor_pending. tcp_sendmsg then finds
nothing to bridge (`kprobe_bridge_no_entry` counter ticks up), tc egress
sees the encrypted packets but can't match, no rewrite. Silent failure
— no error log, no counter except the bridge miss.

Fix: lift the wbio offset out of the C `#define` and into the per-binary
`tls_offset_config` map, pushed at AttachTLS time alongside the existing
SSL→WRL/EncCtx/Algctx/H chain. ssl_read_fd reads it via a new
resolve_wbio_offset() helper that walks current task → mm → exe_file →
i_ino (matching the existing pattern in bpf_uretprobe_evp_cipher_init)
and falls back to the historical 88 when the map has no entry yet (cold
path early in a process's lifetime, before pushTLSOffsets runs — keeps
3.2+ behavior identical to today even in the race).

Verification:
  - 3.0.13 wbio=24 confirmed empirically on Ubuntu 24.04 aarch64 via a
    standalone SSL_set_bio + memory-scan test (rbio at 16, wbio at 24).
  - 3.2+ wbio=88 preserved from the existing hardcoded value; this PR
    doesn't change behavior for those workloads.
  - `TestOpensslOffsetTable_SSLToWBIO` locks in the table values and
    rejects any future entry with SSLToWBIO=0 (which would silently
    regress to the fallback).
