feat(cws): Use task_storage map for capabilities_contexts (#58472)

### What does this PR do?

Back `capabilities_contexts` with a task storage map when `use_syscall_task_storage` is enabled, the same way as the `syscalls` map. The LRU hash map is kept as the fallback on kernels without task storage support.

Accesses go through new `get_capabilities_context` / `new_capabilities_context` / `delete_capabilities_context` helpers, and the cleanup on thread exit becomes a no-op with task storage since the storage is freed along with the thread.

### Motivation

`capabilities_contexts` only carries per-thread state between the capability hooks of the current thread (override_creds depth, checked capability, pending host user namespace capability) and is never read from user space, which makes it a natural fit for task storage:
- a context can't be inherited by a thread reusing the tid
- a context can't be evicted under pressure anymore. With the LRU, losing an entry drops the `override_creds` depth, so capability checks made under overridden credentials end up attributed to the process.

### Describe how you validated your changes

Built all the prebuilt eBPF variants (with and without task storage). The verifier and the behavior are covered by the capabilities functional tests run in CI.
