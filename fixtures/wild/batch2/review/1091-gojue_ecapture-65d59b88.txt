Android 17 (API 37) BoringSSL: version offsets + TLS 1.3 keylog client/server + length fixes (#1029)

* feat(android): add BoringSSL a_17 offsets (Android 17 / API 37)

On Android 17, eCapture derives the eBPF bytecode name from
`ro.build.version.release` (`config_ecandroid.go` -> `boringssl_a_<rel>`), asks
for a nonexistent `boringssl_a_17_kern.o`, and silently falls back to
`boringssl_a_13_kern.o` — the wrong struct offsets, so TLS 1.3 keylog/decrypt
fails. This adds the missing a_17 support.

Offset generator (utils/boringssl-offset.c) — compile against android17-release:
- `ssl_cipher_st.id` (uint32) was renamed to `protocol_id` (uint16) in Android 17.
  Detect it with a type trait (same pattern as the existing ssl_st.version /
  ssl3_state.version probes) and emit SSL_CIPHER_ST_ID from whichever field
  exists, so the generated macro name stays stable. On a_13..a_16 the trait
  selects `id` (unchanged behaviour).
- `bio_st` / `bio_method_st` are opaque in the public headers; include
  `<crypto/bio/internal.h>` for their definitions. That header is present in
  android13/15/16-release too (verified), so generation for the older tags is
  unaffected.

Generated kern/boringssl_a_17_kern.c (offsetof against the android17-release
tag). The only deltas vs a_16 are the SSL_HANDSHAKE tail (NEW_SESSION
0x5f0->0x7d0, EARLY_SESSION, HINTS, CLIENT_VERSION); the TLS 1.3 secret path
(BSSL__SSL_HANDSHAKE_MAX_VERSION 0x1e, SSL3_STATE hs 0x118, client_random 0x30,
exporter 0x182) is unchanged.

Wiring:
- variables.mk: build kern/boringssl_a_17.
- internal/probe/openssl/libs.go: map "boringssl_a_17" -> boringssl_a_17_kern.o.
- utils/boringssl_android_offset.sh: generate a_17 from the android17-release tag.

* android a_17: restore SSL3_STATE traffic-secret offsets + generate them; add test

Codex P1: the generated a_17 header omitted the four
BSSL__SSL3_STATE_{SERVER,CLIENT}_TRAFFIC_SECRET_0[_LEN] macros, so
uretprobe_bssl_do_handshake fell back to boringssl_masterkey.h's older-layout
defaults (client 0x150, lens 0x1b0/0x1b1) and produced unusable keylog output.

- utils/boringssl-offset.c: emit the four macros from the struct itself, guarded
  to the Android 16+ InplaceVector layout (SSL3_STATE.version present). SERVER =
  write_traffic_secret, CLIENT = read_traffic_secret; each _LEN is the size_ byte,
  computed as (next consecutive vector's offset) - 1, robust to padding. Pre-A16
  raw-array headers are untouched (masterkey.h owns them there).
- kern/boringssl_a_17_kern.c: regenerated — now carries
  SERVER 0x120 / CLIENT 0x151 / SERVER_LEN 0x150 / CLIENT_LEN 0x181 (matches a_16).
- test/offsets: TestBoringSSLTrafficSecretOffsets parses every boringssl_a_*_kern.c
  and, for the A16+ layout, asserts the four macros are present and satisfy the
  InplaceVector invariants (CLIENT=SERVER+0x31, SERVER_LEN=CLIENT-1,
  CLIENT_LEN=SERVER_LEN+0x31, size_ 32..48 past storage). Fails without this fix.

Verified end-to-end: built eCapture for Android arm64 (nocore) with this a_17,
ran `-m keylog` on an Android-17 (API 37) image; it loads boringssl_a_17_kern.o,
attaches, and the SSL3_STATE application-traffic secret it extracts decrypts real
TLS 1.3 traffic (recovered live HTTP/2 request headers offline).

* fix(boringssl): correct TLS 1.3 keylog client/server labels and secret length

Two pre-existing defects in the BoringSSL TLS 1.3 keylog path, independent of the
Android version offsets. Both only affect keylog/pcap output (text mode never reads
traffic secrets), so ordinary use did not surface them.

1) Client/server label swap. bssl::SSL3_STATE stores role-relative secrets
   (write_traffic_secret, read_traffic_secret); NSS keylog labels are absolute
   (CLIENT_TRAFFIC_SECRET_0 is the client's secret). uretprobe_bssl_do_handshake
   filled server_traffic_secret_0_ from write and client_traffic_secret_0_ from
   read unconditionally, which is correct only for a server endpoint. For a client
   (the common Android capture) both labels are reversed, and Wireshark cannot
   decrypt. Fix: read ssl_st.server and map by role. The role byte is added to the
   offset generator (ssl_st.server is a bool bitfield; its byte is
   offsetof(renegotiate_mode)+sizeof(enum), = 0xa4 on android17-release). The kern
   change is gated on #ifdef BSSL__SSL_ST_SERVER, which only a_17 defines, so
   a_13..a_16 keep their exact prior mapping.

2) Secret length over-read. The BoringSSL event carries the TLS 1.3 hash length in
   the slot the Go decoder reads as CipherId (mastersecret_bssl_t.hash_len). The
   length switch matched it against real cipher ids (0x1301/2/3), missed, and fell
   to default = EvpMaxMdSize (64), emitting 128-hex secrets that Wireshark rejects.
   Fix: in the default branch only, treat a CipherId in (0, EvpMaxMdSize] as the
   hash length (32=SHA-256, 48=SHA-384). The explicit OpenSSL cipher cases are
   untouched.

Tests: TestKeylogHandler_TLS13_BoringSSLHashLen asserts a hash_len of 32 yields
64-hex (32-byte) CLIENT and SERVER lines, not 128.

Validated on an Android 17 image: the length is now 32 bytes, and the secret the
role branch selects decrypts real TLS 1.3 traffic. The 0xa4 role offset is
offsetof-verified against android17-release; a full label check needs a release
device (the test image is aosp-main, ahead of the tag).
