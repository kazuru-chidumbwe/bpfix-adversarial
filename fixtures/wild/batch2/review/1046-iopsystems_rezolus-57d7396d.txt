fix(cpu)!: correct cpu_bandwidth quota/period, add fentry twins (#1168)

* fix(cpu)!: correct cpu_bandwidth quota/period, add fentry twins

Fixes #1166 and migrates cpu_bandwidth to fentry in one change, because the two
are entangled: the correctness bug is only visible once you read the typed args.

The tg_set_cfs_bandwidth kprobe read PARM2 as `struct cfs_bandwidth*` and
dereferenced it, but the kernel signature is
`tg_set_cfs_bandwidth(struct task_group *tg, u64 period, u64 quota, u64 burst)`
-- PARM2 is `period` (a u64), not a pointer. On modern kernels that dereferences
the period value as an address, faults, and reads 0, so
cgroup_cpu_bandwidth_quota/period were wrong. Verified on delta (6.12): setting
cpu.max="50000 100000", the kprobe's arg1 was 0x5f5e100 (=100000000, the period
value) while the real period/quota sat in arg1/arg2 as plain u64s.

Read period/quota directly from the args in both paths -- the fentry twin gets
them typed, the kprobe reads PARM2/PARM3 -- and extract shared handlers for all
three functions (tg_set_cfs_bandwidth, throttle_cfs_rq, unthrottle_cfs_rq).
throttle/unthrottle were already correct (single cfs_rq* arg); they gain fentry
twins too. fentry needs BTF, so the kprobe twins stay as the CO-RE-only fallback
and disabled_programs picks one set on kernel_has_btf().

The `!` marks the metric-value change: cgroup_cpu_bandwidth_quota/period go from
0 to their real values on kernels where the old read faulted.

Both BPF targets compile; macOS build + tests + clippy clean.

* fix(cpu_bandwidth): report unlimited quota, and pick fentry on the target not the kernel

Three follow-ups from review of the quota/period fix.

**`cpu.max = max` published a garbage quota.** Reading the args means
RUNTIME_INF now reaches userspace, where `quota as i64` turned it into -1
by two's-complement accident on a gauge documented as nanoseconds. Every
cgroup with no CPU limit hits this -- it is what a Kubernetes pod without
a limit writes -- so name the sentinel, test it, and say so on the metric.
It stays -1: negative cannot be read as a nanosecond count, and 0 is what
an unwritten gauge slot already reads as.

**`kernel_has_btf()` is the wrong question for choosing fentry.** It asks
whether the kernel has BTF at all; an fentry program needs ITS OWN target
in that BTF, and libbpf resolves attach_btf_id at LOAD time -- which
BpfBuilder treats as fatal for the whole skeleton. All three hooks here
live behind CONFIG_CFS_BANDWIDTH, so on a kernel built without it the
fentry twins would fail to load and take the sampler with them, where the
kprobe twins merely miss at attach (ENOENT, tolerated, reported as
unsupported). Adds `kernel_btf_has_funcs()` and selects on that instead.

**A typo in `disabled_programs` is invisible and doubles counters.** The
existing debug guard covers declared intents and labels but not this
list, and a name matching no program leaves both twins of that hook
autoloaded -- each running the shared handler, so every `array_add` in it
applies twice. Extend the guard.

Also logs both twins' instruction counts rather than only fentry's, which
on a kprobe kernel named three programs that were not loaded.

fexit was considered for `tg_set_cfs_bandwidth` and rejected: it would
record only what the kernel accepted, but an fexit program's return value
sits at arg slot `nr_args`, and `burst` was only added to that function in
5.14 (f4183717b370). On a 3-arg kernel -- 5.10 LTS among them -- slot 4 is
past the end and the verifier rejects the program at load, costing the
throttling counters too. The reasoning is recorded in the C file so the
next reader does not retry it. The unused `burst` in the fentry prototype
is safe for the opposite reason: nothing reads it, so clang emits no load
for the slot and the verifier never checks it against the target's arity
(confirmed in the disassembly).

Both BPF targets compile, 6 programs each. cargo check/test (687)/clippy/
fmt clean on macOS -- which does not compile the Linux-only Rust here.
