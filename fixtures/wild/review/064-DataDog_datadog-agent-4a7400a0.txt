[CNM-5355] Improve protocol_classifier_entrypoint performance (#56780)

### What does this PR do?

Reduces the per-packet cost of `socket__classifier_entry` (`protocol_classifier_entrypoint()`):

- **Early exit for TLS flows.** Once a flow's encryption layer is known, return unless the record is a ClientHello/ServerHello. The socket filter can't see past TLS (USM classifies the inner protocol from decrypted data in separate uprobe programs), so the only remaining work is extracting handshake tags. This covers every flow known to be TLS, including ones whose handshake was never seen. Letting CH/SH through also re-parses tags for a new connection that reuses a stale `connection_protocol` entry's tuple, as long as that entry has no application layer set.
- **Move the early exits ahead of `classification_context_init()`,** so fully classified and TLS flows skip the per-CPU context setup and payload copy.
- **Look up the protocol stack once and copy it by value** (4 bytes). All read-only checks share that single lookup; writes still go through `get_or_create_protocol_stack()`, and `init_routing_cache()` still gets `NULL` when there's no entry, so tail-call routing is unchanged.

For every record it now skips, `main` already returned without classifying, just after paying for context init. It does not set `FLAG_FULLY_CLASSIFIED`, so later protocols (e.g. USM-decrypted inner protocols) still merge into connection stats (`stats.h`).

A second commit adds a `TestTLSClassification/Stale-TLS-Entry` regression test.

### Motivation

While investigating a customer-reported performance issue (NTWK-684 / CNM-5355), the classifier was found running in full for every packet of long-lived flows (e.g. curl/https downloads of large files). TLS flows never become "fully classified", so they never hit the existing early exit.

The by-value copy also avoids an older-verifier rejection: on kernels like 4.14, a nullable map-value pointer that is spilled across a helper call reloads as an untracked scalar (`R5 invalid mem access 'inv'`). Copying the struct means no map-value pointer is held across `is_tls()` or `classification_context_init()`.

### Describe how you validated your changes

- KMT on `amazon_4.14` and `amazon_5.4`: `TestUSMSuite` and `TestTracerSuite` `TestProtocolClassification` and `TestTLSClassification` pass for CO-RE, prebuilt and runtime-compiled. `TestTLSClassification` asserts ClientHello/ServerHello tags, so the handshake path is intact.
- New `Stale-TLS-Entry` case (Ubuntu 24.04, 6.8): marks the tuple as TLS in `connection_protocol` before the handshake, then asserts the connection still gets its TLS tags. It passes for runtime-compiled, CO-RE and fentry. It also fails against an early exit that lets only ServerHellos through, a regression the existing per-version cases don't catch.
- AKS A/B, 7.83.3 vs. this branch (fentry, USM off, 10-minute runs of Kafka, in-cluster nginx HTTP and Azure Premium blob HTTPS workloads):
  - `socket__classifier_entry` is 9–23% cheaper per call on every node: servers the most (Kafka broker −21.5%, nginx server −23%), clients −9% to −12%.
  - TLS blob client: ≈ 0.4–0.5 cores saved and +2.1% throughput on a CPU-bound node.
  - Kafka broker ≈ 0.06–0.18 cores; nginx ≈ 0.15 cores (server + client).
