fix(driver/modern_bpf): fix verifier and recvmmsg/sendmmsg on kernel 6.19+

Kernel 6.19+ introduced stricter BPF verifier behavior (e.g. commit f597664
SCC analysis for bpf_loop() callbacks), which caused recvmmsg and sendmmsg
to hit the 1M verified-instruction limit and the 512-byte combined stack
limit across the program, bpf_loop callback, and callees.

Changes:

- Add __noinline wrappers for auxmap helpers (auxmap__store_socktuple_param,
  auxmap__store_iovec_data_param, auxmap__submit_event) used inside
  bpf_loop() callbacks so they are verified once as subprograms and reused,
  keeping callback complexity under the verifier limit.

- Introduce apply_dynamic_snaplen_port_range(), a slim port-range-only
  variant of apply_dynamic_snaplen for recvmmsg/sendmmsg. The full
  apply_dynamic_snaplen has large locals (msg_mh union, DPI buf, switch)
  that push the 3-frame stack over 512 bytes; this variant only contains
  the port-range path used by these programs.

- Remove recvmmsg/sendmmsg handling from the main apply_dynamic_snaplen
  switch; they now use apply_dynamic_snaplen_port_range in the callback.

- In recvmmsg/sendmmsg bpf_loop callbacks: read mmsghdr fields individually
  with BPF_CORE_READ_USER instead of bpf_probe_read_user of the full
  struct, and support ia32 (compat_mmsghdr) so stack use stays within
  limits. Use BPF_CORE_READ_USER for sin_port/sin6_port when falling back
  to userspace sockaddr for port_remote to fix non-CORE access.

- Simplify callback context: stop passing syscall args through the context
  struct; use only fd and mmsghdr pointer and read per-message data inside
  the callback.
