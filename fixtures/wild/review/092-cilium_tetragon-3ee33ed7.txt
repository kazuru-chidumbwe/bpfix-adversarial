celbpf: deal with multiple kernels

Loading the programs in 5.4 and 4.19 fails with:

   ; tail_call(ctx, tailcalls, TAIL_CALL_ARGS);
        3573: (bf) r1 = r6
        3574: (18) r2 = 0xffff888138f0e400
        3576: (b7) r3 = 3
        3577: (85) call bpf_tail_call#12
        tail_calls are not allowed in programs with bpf-to-bpf calls

This is because tail-calls cannot mix with bpf-to-bpf calls for these
kernel versions. Moreover, even if we eliminate the cel_expr() call, the
program fails to load on 4.19 due to a large instruction count.

For 4.19 kernels (!defined(__LARGE_BPF_PROG)), the stubs are completely
removed from the BPF object, and for later kernels we force the
cel_expr() call to be a bpf-to-bpf call.

From userspace, we introduce two functions:
 - celbpf.EnabledInBPF() to indicate whether the cel_expr stubs are present in
   the bpf code.
 - celbpf.Supported() to indicate whether we can support CEL exprssions.

celbpf.Supported() uses  aruntime check to determine whether the
kernel allows mixing bpf and tail calls [^1].

for the case where EnabledInBPF() && !Supported(), we replace the call
of cel_expr() with setting R0 to 0 and remove the cel_expr() function
from the instructions. (This is the reason why we need the the
cel_expr() to always be a bpf-to-bpf call.)

[^1]: This capability was implemented in 5.10
(https://lore.kernel.org/bpf/20200829231925.GB31692@ranger.igk.intel.com/T/),
so it's between our two kernel variants  (5.4 and 6.1)
